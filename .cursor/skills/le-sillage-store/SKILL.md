# Le Sillage Store

Le Sillage is a Philippine retail perfume storefront and admin portal built on Next.js 16 App Router, Drizzle ORM with Supabase Postgres (via the `postgres` driver — matching LapTrip's stack), Auth.js (Google + email/password; Facebook is wired but switched off in `configuredOAuthProviders`), Gmail SMTP for notifications, and Vercel Blob for images and (a separate private store) payment receipts. There is no payment gateway — payment is manual via uploaded QR receipts.

## Core business rules

- Product types: `FULL_BOTTLE`, `PARTIAL`, `DECANT`. A product can have more than one SKU (e.g. two sizes, or — for a decant — two provenances at the same size). The shop grid card (`ProductCard`) has no size picker or Add to cart/Buy now of its own any more — sizing and buying only happen on the PDP; the card is a single "View" button plus a `hasRetailDecant` badge (`CatalogCardModel`, computed straight from the raw SKU rows in `loadCatalogCards`, no pricing/grouping work). `buildVariantOptions()` in `src/lib/catalog.ts` is the picker builder for the PDP and the cart drawer's "Customize" picker (`getSiblingSkuOptions`) — it groups SKUs by `${sizeMl}::${provenance}::${isTester}` into a two-tier picker: the always-visible tier-1 button names the size, plus provenance when it's worth naming — never for `IN_HOUSE` (a decant's implied default), always for `RETAIL`/`TESTER` (`sizePickerGroupLabel`) — and appends " · Tester" when `isTester` is set on a non-TESTER provenance so a promo-pool bottle isn't collapsed into an unlabeled duplicate. Groups are listed smallest millilitre first, then A–Z by label (`compareSkuOrder` in `src/domain/variant-options.ts`, numeric so 3ML before 10ML). A tier-2 picker renders underneath: for a `FULL_BOTTLE`/`PARTIAL` group it's always shown, even with only one real choice, and it's the customer-facing `BNIB`/`FP`/`BO` choice (`conditionPackagingChoice` in `src/domain/product-type.ts`) collapsing `condition`+`packaging` — `BNIB` means new and boxed, `FP` ("full package") is not-new but still boxed, `BO` is bottle-only; a `PARTIAL` never shows `BNIB` since nothing sets that combination. For a `DECANT` group the tier-2 picker keeps its older, narrower behavior: shown only when the group actually has more than one raw SKU to distinguish, labeled from `condition`/`packaging` directly (`buildConditionPackagingSubOptions` vs. the decant branch, both in `buildVariantOptions`). `findSelectedVariant()` resolves whichever leaf SKU is selected, top-level or a sub-option, into one flat display shape — it lives in `src/domain/variant-options.ts`, not in the `"use client"` `size-picker.tsx`, specifically so Server Components (the PDP) can call it directly.
- Default fulfillment: `FULL_BOTTLE` → `PRE_ORDER`, `PARTIAL`/`DECANT` → `ON_HAND`. Admin can override.
- **Decant fulfillment/stock depends on `sku.provenance`**, not just `productType === "DECANT"` — see `effectiveFulfillment`/`resolveCartCap` in `src/lib/cart.ts` (the single source of truth; `src/lib/catalog.ts` has an equivalent `decantVariantFulfillment` helper for the read-only catalog-card path):
  - `IN_HOUSE` (poured to order from a whole bottle the store owns): fulfillment/cap are computed live from the product's shared `remainingMl` pool via `decantFulfillment()` — never from the SKU's own `stock`/`fulfillment` columns, which are inert for this case. This is what every decant SKU was before the Retail/In-house split existed.
  - `RETAIL` (bought pre-made as a decant directly from the perfumery): a distinct physical unit, handled exactly like a full-bottle SKU — its own `stock`/`fulfillment` columns are the real source of truth, and it can genuinely sell out. Order-time stock reservation (`reserveStockWithinTx` in `src/lib/orders.ts`) branches the same way: `IN_HOUSE` decants reserve against the ml pool (`ML_RESERVED`), `RETAIL` decants reserve per-unit stock (`ORDER_RESERVED`) like any non-decant SKU.
  - The admin product page's per-SKU Provenance/Fulfillment/Stock fields for a decant are one small client component (`src/components/admin/decant-sku-fields.tsx`) — Fulfillment/Stock only render (and only matter) when Provenance is switched to Retail, alongside a manual Cost price/Retail price pair so a Retail decant can be priced independently of the product's reference formula (`upsertSku` branches on this; `resyncSkuPricesForProduct` skips any SKU with `provenance === "RETAIL"` so a "Save product" never overwrites it). In-house is being phased out for new listings: a brand-new decant SKU now defaults to (and can only be) Retail — the "In-house" option only appears in the dropdown at all when that SKU's current stored value is already `IN_HOUSE`, so an existing In-house SKU keeps displaying/saving correctly without offering In-house as a fresh choice anywhere. The 100+ existing In-house SKUs are untouched and keep working exactly as before.
- Stock is tracked for `ON_HAND`. `PRE_ORDER` has no stock cap. `sku.isTester` ("Free tester") is a per-SKU checkbox on **`DECANT`** SKUs that puts that size into the decant-promo free-tester pool — it remains a normal sellable listing (shop, PDP, cart). The free tester is always a decant, so the checkbox is hidden (posted as empty, so no bottle can be flagged) on `FULL_BOTTLE`/`PARTIAL` SKU forms. Availability and reservation follow the decant's provenance exactly like the cart (`testerUnitsAvailable` in `src/domain/promo.ts`, `loadTesterOptions`/`reserveTesterUnit` in `src/lib/orders.ts`): an `IN_HOUSE` tester is one `sizeMl` pour from the product's `remainingMl` (`TESTER_ML_ASSIGNED`/`TESTER_ML_RELEASED` movements, in ml), a `RETAIL` one is a unit of its own `stock` (`TESTER_ASSIGNED`/`TESTER_RELEASED`). Don't confuse this with `sku.provenance = 'TESTER'`, a separate field describing a non-decant physical bottle's origin (shown as a badge, unrelated to the tester-bonus pool).
- Condition (`BNIB`/`SEALED`/`FEW_SPRAYS_MISSING`) and Packaging (`WITH_BOX`/`BOTTLE_ONLY`) only apply to `FULL_BOTTLE`/`PARTIAL` SKUs — hidden (as hidden inputs preserving the stored value) on decant SKU forms, since neither describes a decant.
- "Buy Now" (`src/components/store/buy-now-button.tsx`, `?buyNow=<skuId>:<qty>` on `/checkout`) prices and orders exactly one item with zero cart interaction — it never reads or clears the cart. `createOrderFromCart` (`src/lib/orders.ts`) takes an optional `directItems` input for this path; `src/lib/cart.ts`'s `loadPricedDirectItem`/`loadDirectItemViewForBothMethods` mirror the cart-based pricing functions for it.
- Pricing: store `costPrice` (admin only) and `retailPrice` (customer-visible). Pricing mode determines how `retailPrice` is computed from `costPrice`: percentage markup, fixed markup, or direct price.
- Discounts stack across three independent types but never within a type — one active discount of each type per order, at most:
  - **Item discount**: a product's own `productDiscounts` row, or the admin's site-wide discount (its own card on `/admin/promo`, with optional Starts/Ends dates; the save that turns it on emails every marketing subscriber once — `shouldAnnounceSiteWideDiscount`/`mergeMarketingRecipients` in `src/domain/marketing.ts`) — `bestDiscount()` in `src/domain/discount.ts` picks whichever saves the customer more. `siteWideDiscountFromSettings` (`src/domain/promo.ts`) is the one reader of the site-wide settings, and `isDiscountActive` enforces its date window everywhere a price is computed.
  - **Order discount**: an ORDER-scope promo code, applied after item discounts to the items that aren't already discounted.
  - **Delivery discount**: a DELIVERY-scope promo code, evaluated after the order discount.
  - An order takes at most one ORDER code and one DELIVERY code, together (`groupPromoCodesByScope`/`checkPromoCodeSet` in `src/domain/promo-code.ts`, the same rules for the checkout preview and `createOrderFromCart`). A second code of the same scope is refused, naming the applied one. Cancelling or rejecting releases every redemption on the order (`releasePromoCodeRedemption`).
  - A promo code's minimum-spend condition is always checked against the already-discounted amount at that point in the pipeline, never the original price. A code that would compute to a ₱0 discount against real numbers is rejected outright rather than silently consuming a redemption.
- Promo codes live on `/admin/promo` (Promo codes tab; `/admin/promo-codes` only redirects there), are created at `/admin/promo/new` and edited at `/admin/promo/[promoCodeId]`. They support: percentage or fixed amount, optional minimum spend, first-order-only, once-per-customer, a redemption cap, start/end dates, an optional description (shown in the promo email and Account → Promo codes; the email also states the minimum order), an optional announcement email, and an allowed-customers list (`promo_code_allowed_user`, edited with the searchable `CustomerMultiSelect` on the code's form; empty means every customer, one or more means only those accounts). `withAllowedUsers` (`src/lib/promo-code-access.ts`) loads the list and also honours the older single-customer `restrictedUserId` column, which a save clears. "Add promo code" on a customer's admin page creates a code for just that customer. Listed customers are emailed on request and see the code under Account → Promo codes, and `/promo-code` copies it. Eligibility is re-validated server-side at order creation — never trusted from the client — inside the same transaction as the order insert, with the code row locked (`SELECT ... FOR UPDATE`) so two concurrent checkouts can't both exceed a redemption cap.
- Decant promo: when the discounted merchandise subtotal of decants reaches ₱2,000, the order gets free delivery AND one tester drawn from a brand the customer purchased (`pickTester` matches `brand` only; `upsertSku` copies that onto `sku.testerBrand`). If no compatible tester is in stock or the reserve races and loses, leave the result `PENDING` for admin fulfillment — never `SKIPPED`, never a random unrelated tester. Admin fulfillment is the `TesterPicker` on `/admin/orders/[orderId]` (`adminAssignTester` → `assignTesterToOrder`): a dropdown of every in-stock tester, brand matches first, that can also swap an auto-assigned one; the previous pick is released and the new one reserved in one row-locked transaction, allowed while the order is `RECEIPT_SUBMITTED`/`CONFIRMED`. **`RECEIPT_SUBMITTED → CONFIRMED` is refused while `promoTesterResult` is `PENDING`** (`confirmBlockedReason` in `src/domain/order-state.ts`, enforced in `transitionOrderStatus` and mirrored as a disabled Confirm button with the reason in `OrderRowActions`), so a customer is never confirmed with a promised tester nobody set aside. The receipt-received and payment-verified emails name the assigned tester.
- Delivery: ₱120 flat by default (admin-configurable), pickup is free. Delivery fee is replaced by ₱0 under the decant promo, independent of any delivery-scope promo code (which stacks on top).
- ETAs: `PRE_ORDER` is 3–30 days; `ON_HAND` ordered on Saturday/Sunday qualifies for same-day delivery; otherwise 1–2 days. Mixed orders show both windows.
- Order statuses: delivery `AWAITING_PAYMENT → RECEIPT_SUBMITTED → CONFIRMED → SHIPPED → DELIVERED → COMPLETED`, pickup `AWAITING_PAYMENT → RECEIPT_SUBMITTED → CONFIRMED → READY_FOR_PICKUP → COMPLETED`, plus `REJECTED` and `CANCELLED` (require reason). State transitions are enforced server-side with `never`-checked exhaustive switches. Placing an order sends no email. An order still on `AWAITING_PAYMENT` two hours after it entered that status gets **one** payment reminder with a Pay by time (`paymentReminderSentAt`; `GET /api/cron/payment-reminders`; also `npm run payment-reminders`), and with no receipt after 24 hours it is cancelled automatically (`auto-reject-orders`). A `DELIVERED` order gets a day-2 "did it arrive?" email and completes itself after 3 days. Once `CONFIRMED`, a customer cancel is a request an admin approves or denies (`requestOrderCancellation`/`resolveCancellationRequest`), and a pending request blocks every other status change. The `order_cancelled` email promises a refund when the order was cancelled after `AWAITING_PAYMENT`, and says nothing was charged otherwise.
- Cron jobs: every `/api/cron/*` route runs hourly from the Cloudflare Worker in `workers/auto-reject-cron` (its `JOBS` list, Bearer `CRON_SECRET`), because Vercel Hobby only allows daily crons. That includes `marketing-emails`, which sends the next 15 queued marketing emails (`drainMarketingQueue`). A new cron route goes in that list too; its `vercel.json` entry is only a daily fallback, so the route must be safe to run twice. `npx wrangler deploy` from that folder ships it, and the root `tsconfig.json` excludes `workers` on purpose.
- ON_HAND inventory is reserved at receipt submission in a single DB transaction. Stock is restored exactly once if a receipt-submitted order is later rejected or cancelled (including a `CONFIRMED → CANCELLED` transition, which reserves stock the same as `RECEIPT_SUBMITTED` does).
- Customer accounts are required for checkout, receipt submission, and order history. Browsing and cart editing remain open to guests. Carts merge on sign-in (with a conflict dialog if both a guest and account cart have items).
- Customers never see `costPrice`. Admin never sees payment API integrations because none exist.
- Philippine delivery addresses use cascading Province → City/Municipality → Barangay selects (`PhAddressFields`, backed by the PSGC dataset via `src/lib/ph-locations.ts` and `/api/ph-locations/*`), not freeform text. Region isn't a visible field — it's auto-derived from the chosen province and stored on `addresses.region`/the order's `addressSnapshot`. City and Barangay are disabled until their parent is chosen; Postal code and Street stay free text.

## Storefront

- **/shop** is one page for every shelf. No `?type=` means All (every product type); `?type=DECANT|FULL_BOTTLE|PARTIAL` narrows it. There are no in-page shelf tabs: shelves are chosen from the header's Shop menu (`src/components/store/shop-menu.tsx`, four `ShopTile` cards: All fragrances, Decants, Full bottles, Partials) or, on phones, the same cards in the hamburger menu (`store-header.tsx`). "Shop" in the header is a dropdown button, not a link. Filters: Gender, Shelf (`?category=`), and Stock (`?stock=ON_HAND|PRE_ORDER`, matching each card's own On hand / Pre-order badge; `CatalogFilter.availability`). There is no concentration filter.
- **Sorting**: default is name A-Z. Every sort breaks ties by name A-Z (`compareCardNames` in `src/lib/catalog.ts`), so "Biggest discount" lists all sale items alphabetically, then everything else alphabetically. "Newest" is pure creation order. Catalog reads are cached for 60 seconds (`unstable_cache`, tag `catalog`), so a sort change can take up to a minute to show.
- **Page size**: 20 cards, or 21 while the grid is three columns wide (640-1023px) so every page ends on a full row. The server can't see the screen, so `ShopGridSync` stores the grid width in the `shop_cols` cookie and refreshes once when it changes (`src/lib/shop-grid.ts`). Pagination shows numbered pages at every size (a tighter window on phones).
- **Grid**: one column below 360px, two on phones, three from 640px, then four and five. `ProductCard` defaults to compact sizes for narrow cards and steps up from 576px; its price is one number, "From ₱X" when other options cost more, with the struck-through original beside it (or above it when the card is too narrow). Cards aren't text-selectable.
- **Search** (header search and `?query`) splits the query into words; every word must appear in the name or the brand, in any order (`productSearchCondition`).
- **Homepage** (`src/app/page.tsx`, `src/components/store/home-sections.tsx`): hero with a random discounted full bottle, then "On sale now", Browse by type, "New arrivals", "Try before the bottle" (top-rated decants), Shop by scent family (`ShopTile` cards into `/shop?category=`), How it works, and a slim newsletter band. The three product rails come from one cached read (`src/lib/home-rails.ts`): no product appears twice, and New arrivals/decants show at most two per brand. Rails have Previous/Next arrows from `md` (`rail-carousel.tsx`) that wrap around at the ends (Next on the last card rewinds to the start); on phones middle cards snap to the centre with a quarter of each neighbour showing.
- **Colour**: small gold text uses `text-gold-ink` (a deeper gold in light mode that passes 4.5:1 contrast), never `text-gold`, which is for fills and large accents. The shared `Eyebrow` already does this.
- **Accessibility**: a Skip to content link is the first tab stop (`#main-content` in `src/app/layout.tsx`); links in cards and menus get a visible 2px gold focus ring; the landing-page audit and before-redesign screenshots are in `docs/checkpoints/2026-09-29-landing-before-redesign/` (git tag `landing-before-redesign`).
- **Authenticity**: the promise is a full refund if anything sold is proven fake, final-sale items included. It lives in `policyCopy.returns` (`src/lib/policy-copy.ts`, shown on the product page, cart, cart drawer, and Policies page), the FAQ, and the About page's pillars.

## File layout

- `src/db/` — Drizzle schema + `db()` client. SQL migration scripts and one-off data scripts live in `scripts/` (matching LapTrip: `npm run db:migrate`, `npm run db:seed`). There's no `src/db/seed.ts` — seeding is `scripts/seed.ts`.
- `src/domain/` — money, pricing, discounts, promo codes, decant promo, ETA, cart pricing, checkout totals, and order-state logic. Pure functions only.
- `src/actions/` — Server Actions for cart (`cart-actions.ts`), orders (`order-actions.ts`), promo codes (`promo-code-actions.ts`, `admin-promo-code-actions.ts`), account (`account-actions.ts`), auth (`auth-actions.ts`, `auth-credentials-actions.ts`), and admin (`admin-actions.ts`, `admin-catalog-actions.ts`, `admin-qr-actions.ts`), and the newsletter (`newsletter-actions.ts`: double opt-in sign-up from `subscribe-hero.tsx`, `/newsletter/confirm`, `/unsubscribe`). Marketing email is queued (`marketing_email`, `src/lib/marketing-queue.ts`), carries a signed unsubscribe link plus a `List-Unsubscribe` header, and only reaches `loadMarketingRecipients`: verified opted-in accounts and confirmed newsletter sign-ups. There's no `src/actions/orders.ts` or `src/actions/admin/` subdirectory — admin order-status transitions live in `admin-actions.ts`.
- `src/lib/` — env validation, blob (public images plus the private receipts store), email, rate limits, auth helpers, PH location lookups (`ph-locations.ts`), and formatters.
- `src/app/(store)/` — storefront routes.
- `src/app/account/` — authenticated customer area.
- `src/app/admin/` — protected admin area.
- `src/components/store/` and `src/components/admin/` — UI by surface.

## Mobile-first

Every layout, typography, navigation, and interactive component must be built and tested at narrow viewports (360–414px) first, then enhanced for larger screens.

## Loading states

- Static page chrome (headers, titles, nav, copy that doesn't depend on a DB fetch) renders immediately in `loading.tsx` — never wrap it in a skeleton.
- Only the regions that actually fetch data show a skeleton, and it must be shaped like — and only like — the real content it's replacing; a shared skeleton component reused across routes needs a prop (e.g. `showCount`) wherever one caller's real content differs from another's, so it never skeletons a region that has no matching real content on that route.
- Route-level: every `page.tsx` doing server-side data fetching needs a matching `loading.tsx`. A dynamic segment's own value (e.g. `[category]`, `[skuId]`) isn't readable inside `loading.tsx` — Next.js doesn't pass `params`/`searchParams` to it — so that one piece stays a skeleton even on an otherwise fully-static fallback.
- Same-route client interactions that re-fetch via search params (filter tabs, sort, pagination) need their own Suspense boundary keyed to the changing param, since `loading.tsx` alone does not retrigger for query-string-only navigation on the same route.

## Code review checkpoints

`code-review/CHECKPOINT.md` holds the last-reviewed commit SHA; a review scopes to `git diff <that-sha>...HEAD` instead of the whole tree (full baseline only when no checkpoint exists yet, or a full re-audit / specific PR-branch-path target was asked for), and always appends an entry to `code-review/LOG.md` and advances the checkpoint when it finishes — even with zero findings. Full rule and rationale in `.cursor/rules/code-review-checkpoints.mdc` (imported by `CLAUDE.md`).
